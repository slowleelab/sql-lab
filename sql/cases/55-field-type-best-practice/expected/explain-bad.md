## 关键问题

### 问题 1：VARCHAR status 的字符串比较代价

`status VARCHAR(20)` 存中文状态值（'待支付'、'已支付'…），在 utf8mb4 下：

1. **索引 key_len = 82 字节**：是 TINYINT（1 字节）的 82 倍，索引体积大
2. **字符串比较慢**：需逐字节比对字符编码，整数比较是 CPU 单条指令
3. **存储浪费**：'已支付' 占 12 字节，而 TINYINT 只占 1 字节
4. **状态扩展不友好**：新增状态需改字符串，且中文字符串易因编码问题出错

::: warning 状态字段用 VARCHAR 的代价
状态、类型、性别这类**枚举值少且固定**的字段，用 VARCHAR 存中文字符串是典型的类型误用。索引 key_len 膨胀数十倍，比较代价高，还占用更多行内存储。正确做法是用 TINYINT 存整数编码，值映射在应用层或数据字典维护。
:::

### 问题 2：FLOAT amount 的精度问题

`amount FLOAT` 存订单金额，FLOAT 是 IEEE 754 单精度浮点数（4 字节），**只能保证约 7 位有效数字**：

1. **99.90 存为 99.9000015258789**：二进制无法精确表示十进制小数
2. **等值查询失效**：`WHERE amount = 99.90` 可能返回 0 行
3. **财务风险**：金额计算累加误差，对账时金额对不上
4. **范围查询也受影响**：`amount > 99.90` 的边界行为不可靠

```
FLOAT 存储机制:
  99.90 -> 二进制浮点近似 -> 99.90000152587890625
  读取时返回 99.9（显示截断），但内部值并非精确的 99.90

DECIMAL 存储机制:
  99.90 -> 每两位存一个字节（BCD 编码）-> 精确存储 99.90
  读取返回精确的 99.90，无任何偏差
```

::: warning 金额字段绝不能用 FLOAT
任何涉及金额、利率、比例的字段，**一律用 DECIMAL**。FLOAT/DOUBLE 的精度问题会导致等值查询失效、对账不平、累加误差。DECIMAL(10,2) 可精确存储到分，占用 5 字节，比 FLOAT 多 1 字节，但换来的是精确无误。
:::

### 问题 3：VARCHAR(50) phone 的索引膨胀

`phone VARCHAR(50)` 实际手机号仅 11 位，VARCHAR(50) 严重过大：

1. **索引 key_len = 202 字节**：是 VARCHAR(20)（82 字节）的 2.5 倍
2. **索引体积膨胀**：10 万行索引多占约 60% 空间
3. **buffer pool 浪费**：大索引挤占缓存，热数据易被驱逐
4. **写入变慢**：B+ 树节点大，插入与分裂成本高

::: tip VARCHAR 长度按实际需要设定
VARCHAR(N) 的索引按 N 计算最大 key_len（utf8mb4 下 N×4+2），而非实际存储长度。即使手机号只有 11 位，VARCHAR(50) 的索引仍按 50×4+2=202 字节计算。**长度按业务最大需要设定，留过多余量会直接膨胀索引**。
:::

### 问题 4：VARCHAR is_deleted 的冗余

`is_deleted VARCHAR(5)` 存 'true'/'false'，应改 `TINYINT(1)`：

1. **存储浪费**：'false' 占 5 字节，TINYINT(1) 占 1 字节
2. **比较代价高**：字符串比较 vs 整数比较
3. **语义不清**：布尔值用字符串表达，不如 TINYINT(1) 直观

## 5.7 vs 8.0 差异

- 两版本的 FLOAT 精度问题一致（均为 IEEE 754 单精度）
- 两版本的 VARCHAR 索引 key_len 计算一致（N×4+2，utf8mb4）
- 8.0 的 DECIMAL 在内部存储上更紧凑，但精度行为两版一致
