> good 表通过合理选择 TINYINT、CHAR、VARCHAR(20)、DECIMAL，
> 显著缩减索引 key_len、消除精度问题、降低存储开销。

### 金额等值查询对比

## 为什么更好

good 表的类型选择带来的收益：

1. **status TINYINT**：key_len 从 82 降到 1，索引体积缩减 99%，整数比较比字符串快
2. **amount DECIMAL**：精确存储到分，等值查询可靠，对账无误差
3. **phone VARCHAR(20)**：key_len 从 202 降到 82，索引体积缩减 59%，buffer pool 更友好
4. **gender CHAR(1)**：定长 1 字节，比 VARCHAR(10) 节省空间且比较快
5. **is_deleted TINYINT(1)**：1 字节整数，比 VARCHAR(5) 的 'false'（5 字节）节省 80%
6. **remark VARCHAR(500)**：合理长度，NULL 值在行内不占空间（仅 NULL 标志位）

### VARCHAR 空值不占行内空间的特性

```
InnoDB 行格式（COMPACT/DYNAMIC）:
  - VARCHAR 列存储: 1~2 字节长度前缀 + 实际数据
  - NULL 值: 不存储长度前缀和数据，仅在 NULL 标志位占 1 bit
  - 所以 remark=NULL 的行，remark 列几乎不占行内空间

本案例 remark 一半为 NULL:
  - 有值行: 存储实际字符串（约 40 字节）
  - NULL 行: 仅占 NULL 标志位（1 bit），几乎不占空间
  - 这也是 VARCHAR 相对 CHAR 的核心优势: 按实际长度存储，不固定填充
```

::: tip 类型选择的核心原则
1. **枚举值用 TINYINT**：状态、类型、布尔值，少占空间、比较快、索引小
2. **金额用 DECIMAL**：精确到分，杜绝精度问题
3. **VARCHAR 长度按需设定**：索引按定义长度算 key_len，过长直接膨胀索引
4. **定长短串用 CHAR**：性别、状态码等固定长度字符用 CHAR，省去长度前缀
:::

## 5.7 vs 8.0 差异

| 特性 | 5.7 | 8.0 |
|------|-----|-----|
| TINYINT/VARCHAR 索引 key_len | 一致 | 一致 |
| FLOAT 精度问题 | 一致（IEEE 754） | 一致 |
| DECIMAL 精度行为 | 精确 | 精确 |
| DECIMAL 内部存储 | 每位 4 bit + 符号 | 更紧凑（部分场景） |
| VARCHAR NULL 存储 | 行内不占空间 | 一致 |
| CHAR 尾部空格 | 保留 | 8.0 默认 PAD SPACE（填充） |

::: tip 两版核心一致
类型选择的核心原则在 5.7 和 8.0 完全一致：枚举用 TINYINT、金额用 DECIMAL、VARCHAR 按需定长。8.0 对 DECIMAL 的内部存储做了一些优化，但对外精度行为和 key_len 计算与 5.7 相同。
:::
