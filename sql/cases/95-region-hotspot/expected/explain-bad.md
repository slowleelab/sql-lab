# EXPLAIN 参考结果 - bad.sql（Region 热点诊断与分析）

## TiDB v7.5.1（30 万 t_region_test 行）

---

### 场景1: 初始 Region 分布查看

```sql
SHOW TABLE t_region_test REGIONS;
```

典型输出（初始状态，表仅有一个或少个 Region）：

```
+-----------+-----------------------------+-----------------------------+-----------+---------------------+------------+
| REGION_ID | START_KEY                   | END_KEY                     | LEADER_ID | APPROXIMATE_SIZE    | APPROXIMATE_KEYS |
+-----------+-----------------------------+-----------------------------+-----------+---------------------+-----------+
|      1021 | t_152_                      | t_152_00                    |      1022 |           135266304 |     300000 |
+-----------+-----------------------------+-----------------------------+-----------+---------------------+-----------+
```

#### 字段说明

| 字段 | 含义 | 本次观察 |
|------|------|---------|
| `REGION_ID` | Region 唯一标识 | 1021（初始只有一个 Region） |
| `START_KEY / END_KEY` | Region 管辖的 Key 范围 | `t_152_` 到 `t_152_00`（覆盖全表） |
| `LEADER_ID` | 该 Region Leader 所在 TiKV 的 store_id | 1022 |
| `APPROXIMATE_SIZE` | Region 近似大小（字节） | ~129 MB（刚好超过默认 96MB Split 阈值） |
| `APPROXIMATE_KEYS` | Region 近似 Key 数量 | 300,000 |

---

### 场景2: 数据倾斜验证

```sql
SELECT ts, COUNT(*) AS cnt
FROM t_region_test
GROUP BY ts
ORDER BY cnt DESC
LIMIT 10;
```

```
+---------------------+--------+
| ts                  | cnt    |
+---------------------+--------+
| 2026-07-28 12:00:00 | 150000 |
| 2026-07-15 08:23:00 |   5123 |
| 2026-07-10 14:47:00 |   5118 |
| 2026-07-03 09:12:00 |   5099 |
| ...                 |   ...  |
+---------------------+--------+
```

#### 分析

热点值 `2026-07-28 12:00:00` 独占 15 万行（50%），是其他任何 ts 值（约 5 千行）的 **30 倍**。这意味着：

- `idx_ts` 索引中，热点值对应的索引 Key 会集中在 **同一个 Region** 的 Key Range 内
- 所有针对该 ts 值的写入，都会路由到该 Region 的 Leader TiKV 节点

---

### 场景3: 集中写入后的 Region 膨胀

执行 5 万行集中写入后：

```sql
INSERT INTO t_region_test (val, ts)
SELECT val, '2026-07-28 12:00:00'
FROM t_region_test
LIMIT 50000;

SHOW TABLE t_region_test REGIONS;
```

```
+-----------+-----------------------------+-----------------------------+-----------+---------------------+-----------+
| REGION_ID | START_KEY                   | END_KEY                     | LEADER_ID | APPROXIMATE_SIZE    | APPROXIMATE_KEYS |
+-----------+-----------------------------+-----------------------------+-----------+---------------------+-----------+
|      1021 | t_152_                      | t_152_00                    |      1022 |           189000000 |     350000 |
+-----------+-----------------------------+-----------------------------+-----------+---------------------+-----------+
```

**观察要点**：

- `APPROXIMATE_SIZE` 从 ~129MB 增长到 ~189MB（增长 46%）
- 即便 Region 大小超过了默认的 96MB Split 阈值，TiDB 可能还没有立即触发 Split（Split 有调度延迟）
- 该 Region 所在的 TiKV 节点（store_id=1022）将成为写入热点

### 场景4: 热点形成机制

```
┌──────────────────────────────────────────────────────────────┐
│  t_region_test 表的 Key 空间布局                              │
│                                                              │
│  Row Key:  t_{table_id}_r_{row_id}                           │
│  Index Key: t_{table_id}_i_1_{ts_value}_{row_id}             │
│                                                              │
│  Region 1 ─────────────────────────────────────               │
│  [t_152_ .................................. t_152_00]         │
│                                                              │
│  所有 20 万行（热点值）的 idx_ts 索引 Key 都集中在：            │
│    t_152_i_1_2026-07-28 12:00:00_{row_id}                    │
│                                                              │
│  这些 Key 全部落在 Region 1 的 Key Range 内                    │
│  → Region 1 的 Leader TiKV 节点承受所有写入压力                │
└──────────────────────────────────────────────────────────────┘
```

#### 热点的两种类型

| 热点类型 | 触发条件 | 诊断方法 | 本案例表现 |
|---------|---------|---------|-----------|
| **写入热点** | 大量 INSERT/UPDATE 集中命中同一 Region | `SHOW TABLE ... REGIONS` 观察大小增长 | 索引 idx_ts 的 Region 持续膨胀 |
| **读取热点** | 大量 SELECT 集中命中同一 Region | PD Dashboard → Hot Read | 热点 ts 值被频繁查询 |
| **Leader 热点** | 多个 Region 的 Leader 集中在同一 TiKV | PD Dashboard → Store Load | Leader 集中在某 TiKV 节点 |

---

### 场景5: 热点对集群的影响

```
写入倾斜 → 单 Region 热点
    │
    ├── TiKV 节点负载不均
    │   · 热点节点 CPU 飙至 100%
    │   · 其他节点 CPU < 30%（资源浪费）
    │
    ├── 写入延迟劣化
    │   · Raft 复制压力集中在单节点
    │   · apply 延迟增加 → 整体写入 P99 恶化
    │
    ├── PD 调度压力
    │   · PD 检测到热点后尝试调度 Region
    │   · 但写入持续涌入，调度跟不上写入速度
    │
    └── GC 阻塞（极端情况）
        · 单 Region 过大 → 压缩和 GC 耗时过长
        · 可能触发 "GC worker too busy" 告警
```

---

### 核心问题总结

bad.sql 中暴露的 3 个问题：

1. **Region 未预分裂**：建表后未执行 `SPLIT TABLE`，所有数据集中在一个或少个 Region 中。即使达到 96MB 自动分裂阈值，分裂也有延迟。

2. **数据倾斜导致索引热点**：`idx_ts` 索引上 50% 的数据共享同一个 ts 值，该值的索引 Key 全部落在同一个 Region，形成写入热点。

3. **缺少 SCATTER**：即使 Region 分裂后，Leader 可能仍然集中在某些 TiKV 节点上，没有通过 `SCATTER` 打散 Leader 分布。
