# EXPLAIN 参考结果 - bad.sql（三种时间格式反模式）

> 本案例 `t_time_bad.created_at` 是 `VARCHAR(20)`，建有 `idx_created` 索引。三种反模式分别演示：字符串范围比较的语义脆弱性、DATE_FORMAT 致索引失效、BETWEEN 字符串日期边界漏数据。以下为 20 万行数据下的 EXPLAIN 与结果分析。

## 反模式 1: 字符串范围比较 `created_at >= '2026-07-01' AND created_at < '2026-07-02'`

```sql
EXPLAIN SELECT id FROM t_time_bad
WHERE created_at >= '2026-07-01' AND created_at < '2026-07-02';
```

```
+----+-------------+------------+------------+-------+---------------+-------------+---------+-------+------+----------+-----------------------+
| id | select_type | table      | partitions | type  | possible_keys | key         | key_len | ref   | rows | filtered | Extra                 |
+----+-------------+------------+------------+-------+---------------+-------------+---------+-------+------+----------+-----------------------+
|  1 | SIMPLE      | t_time_bad | NULL       | range | idx_created   | idx_created | 22      | NULL  |  547 |   100.00 | Using index condition |
+----+-------------+------------+------------+-------+---------------+-------------+---------+-------+------+----------+-----------------------+
```

| 字段 | 值 | 分析 |
|------|-----|------|
| type | `range` | 走了索引范围扫描 |
| key | `idx_created` | VARCHAR 列的索引被使用 |
| key_len | `22` | VARCHAR(20) 在 utf8mb4 下最大 20*4+2=82，实际 key_len 取决于排序规则与实际值 |
| rows | ~547 | 预估扫描行数 |
| Extra | `Using index condition` | 索引条件下推 |

### 为什么仍是反模式

**虽然能走索引，但语义是"字符串字典序比较"而非"时间比较"**。当所有值都严格遵循 `YYYY-MM-DD HH:MM:SS` 补零格式时，字典序恰好与时间序一致，表面查对了。但这是脆弱的巧合：

- 若混入非补零格式（如 `2026-7-1 8:0:0`），字典序立刻错乱，`'2026-7-1 8:0:0'` 与 `'2026-07-01 08:00:00'` 的排序、范围比较结果都错。
- 无法用时间函数（`DATEDIFF`、`DATE_ADD`、`YEAR()` 等）做日期运算，用了就要隐式转换或包裹函数，又回到反模式 2。
- 排序是字符串排序，格式不统一时 `ORDER BY created_at` 结果错误。
- 存储无校验：`'2026-13-45 99:99:99'` 这种非法时间也能存进去，查询时才暴露问题。

## 反模式 2: DATE_FORMAT 函数包裹字段致索引失效

```sql
EXPLAIN SELECT id FROM t_time_bad
WHERE DATE_FORMAT(created_at, '%Y-%m-%d') = '2026-07-01';
```

```
+----+-------------+------------+------------+------+---------------+------+---------+------+--------+----------+-------------+
| id | select_type | table      | partitions | type | possible_keys | key  | key_len | ref  | rows   | filtered | Extra       |
+----+-------------+------------+------------+------+---------------+------+---------+------+--------+----------+-------------+
|  1 | SIMPLE      | t_time_bad | NULL       | ALL  | NULL          | NULL | NULL    | NULL | 199687 |   100.00 | Using where |
+----+-------------+------------+------------+------+---------------+------+---------+------+--------+----------+-------------+
```

| 字段 | 值 | 分析 |
|------|-----|------|
| type | `ALL` | **全表扫描** |
| possible_keys | `NULL` | DATE_FORMAT 函数导致优化器无法使用 idx_created |
| key | `NULL` | 索引完全未被使用 |
| rows | ~199,687 | 扫描全部近 20 万行 |
| Extra | `Using where` | 对每行计算 DATE_FORMAT(created_at) 后再比较 |

### 为什么慢

`idx_created` 索引存储的是原始 VARCHAR 值（如 `2026-07-01 08:00:00`），按 B+ 树字典序排列。`WHERE DATE_FORMAT(created_at, '%Y-%m-%d') = '2026-07-01'` 对索引列施加了 `DATE_FORMAT()` 函数，优化器无法从 B+ 树中直接定位 `DATE_FORMAT(x) = '...'` 的入口（函数转换破坏了索引的有序性），只能放弃索引，全表扫描逐行计算。实际耗时约 100ms+。

::: warning 与案例 04 的关系
本反模式与案例 04（函数操作致索引失效）原理相同，都是"函数包裹字段"破坏索引。区别在于视角：
- **案例 04**：`created_at` 是 `DATETIME`，用 `DATE()` / `DATE_FORMAT()` 包裹导致索引失效，重点是"函数致索引失效"这一通用陷阱。
- **案例 78**：`created_at` 是 `VARCHAR`，开发者因为"存的是字符串"才不得不写 `DATE_FORMAT(created_at, '%Y-%m-%d')` 来取日期部分，重点是"格式选择错误（VARCHAR 存时间）逼出了函数包裹的写法"。根因是类型选错，治本应改用 DATETIME。
:::

## 反模式 3: BETWEEN 字符串日期的边界陷阱

```sql
EXPLAIN SELECT id FROM t_time_bad
WHERE created_at BETWEEN '2026-07-01' AND '2026-07-01';
```

```
+----+-------------+------------+------------+-------+---------------+-------------+---------+------+------+----------+-----------------------+
| id | select_type | table      | partitions | type  | possible_keys | key         | key_len | ref  | rows | filtered | Extra                 |
+----+-------------+------------+------------+-------+---------------+-------------+---------+------+------+----------+-----------------------+
|  1 | SIMPLE      | t_time_bad | NULL       | range | idx_created   | idx_created | 22      | NULL |    1 |   100.00 | Using index condition |
+----+-------------+------------+------------+-------+---------------+-------------+---------+------+------+----------+-----------------------+
```

| 字段 | 值 | 分析 |
|------|-----|------|
| type | `range` | 走了索引范围扫描 |
| key | `idx_created` | 索引被使用 |
| rows | `1` | 预估只扫到 1 行 |
| Extra | `Using index condition` | 索引条件下推 |

### 为什么是反模式：漏掉当天数据

`BETWEEN '2026-07-01' AND '2026-07-01'` 是闭区间，等价于：

```sql
created_at >= '2026-07-01' AND created_at <= '2026-07-01'
```

但 `created_at` 的值形如 `2026-07-01 08:00:00`，字符串字典序比较时：

```
'2026-07-01 08:00:00' >= '2026-07-01'  ->  TRUE   (前缀匹配，更长字符串更大)
'2026-07-01 08:00:00' <= '2026-07-01'  ->  FALSE  (后面多了 ' 08:00:00'，更大)
```

因此 `2026-07-01 08:00:00` 不满足 `<= '2026-07-01'`，**当天 00:00:00 之后的所有数据全部被漏掉**。只有字面量恰好等于 `'2026-07-01'`（即没有时分秒部分）的行才会被命中，几乎查不到任何数据。

### 结果对比

| 查询写法 | 命中行数 | 说明 |
|----------|----------|------|
| `BETWEEN '2026-07-01' AND '2026-07-01'` | **~0** | 漏掉当天几乎全部数据 |
| `BETWEEN '2026-07-01 00:00:00' AND '2026-07-01 23:59:59'` | 正常 | 补齐时分秒，但仍可能漏小数秒，闭区间不优雅 |
| `created_at >= '2026-07-01 00:00:00' AND created_at < '2026-07-02 00:00:00'` | 正常 | **闭开区间，正解**（见 good.sql） |

::: warning BETWEEN 的边界本质
`BETWEEN a AND b` 在 MySQL 中是**闭区间** `[a, b]`，等价于 `>= a AND <= b`。对于时间类型：
- `BETWEEN '2026-07-01' AND '2026-07-01'` 只覆盖"恰好等于 7-1 零点"的一个点，漏掉当天其余时刻。
- `BETWEEN '2026-07-01 00:00:00' AND '2026-07-01 23:59:59'` 看似覆盖全天，但若 DATETIME 有小数秒（`23:59:59.999999`），仍会漏掉最后一秒内的数据。
- **正解是闭开区间** `>= '2026-07-01 00:00:00' AND < '2026-07-02 00:00:00'`，按"天的起点"切分，无歧义、不重叠、不遗漏。
:::

## 三个反模式汇总

| 反模式 | 是否走索引 | 正确性 | 根本问题 |
|--------|-----------|--------|----------|
| 1. VARCHAR 范围比较 `>= '7-1' AND < '7-2'` | 走索引(range) | 脆弱(依赖格式统一补零) | 字符串比较非时间比较，无时间运算能力 |
| 2. `DATE_FORMAT(col, ...) = '7-1'` | **不走索引(ALL)** | 正确 | 函数包裹字段致索引失效，20 万行全表扫描 |
| 3. `BETWEEN '7-1' AND '7-1'` | 走索引(range) | **错误(漏数据)** | 闭区间+字符串日期，漏掉当天 00:00:00 之后数据 |

## MySQL 5.7 差异

5.7 与 8.0 行为一致：反模式 2 均为全表扫描，反模式 1/3 均走 range 范围扫描但存在上述正确性/语义问题。VARCHAR 索引的 `key_len` 在两版下计算方式一致（受字符集与排序规则影响）。
